# Технічні рішення

Коротко: що вирішили, чому, і що було альтернативою. Нове рішення — новий запис унизу.

## 001. Одна репа для фронтенду і бекенду — 2026-11-01

**Рішення:** monorepo: `frontend/`, `backend/`, `content/`, `docs/`.
**Чому:** один розробник, фронт і бекенд змінюються разом, одна історія змін і один README для портфоліо.
**Альтернатива:** дві окремі репи — має сенс, коли є різні команди й окремі релізи.

## 002. Vite SPA, а не Next.js — 2026-11-01

**Рішення:** фронтенд — React SPA на Vite, бекенд — окремий FastAPI.
**Чому:** серверна частина Next.js дублювала б FastAPI. Застосунку за логіном SSR і SEO не потрібні. SPA + REST API — проста схема з чітким розділенням фронтенду і бекенду.
**Альтернатива:** Next.js. Якщо лендингу (v1.0) знадобиться SEO, його можна зробити окремо.

## 003. FastAPI, а не Django — 2026-11-01

**Рішення:** бекенд на FastAPI.
**Чому:** легкий фреймворк без зайвої «магії»: автентифікацію, шари й роботу з базою збираємо самі й повністю контролюємо. Pydantic дає типізацію, схожу на TS/Zod. Python — головна мова для AI-частини продукту.
**Альтернатива:** Django — адмінка, auth і ORM з коробки, але багато «магії». Адмінку для FastAPI за потреби можна взяти готову (SQLAdmin).

## 004. uv для Python — 2026-11-01

**Рішення:** залежності й віртуальне оточення через uv (`pyproject.toml` + `uv.lock`).
**Чому:** сучасний стандарт, швидкий, lock-файл з коробки; ним користується і офіційний Full Stack FastAPI Template. Сам створює `backend/.venv`.
**Альтернатива:** pip + venv + requirements.txt — ті самі ідеї, але вручну і без lock-файла.

## 005. Один Python-проєкт для API і скриптів контенту — 2026-11-01

**Рішення:** скрипти для уроків (валідація JSON, імпорт, генерація) живуть у `backend/`, а не в окремому проєкті.
**Чому:** одна Pydantic-модель уроку перевірятиме JSON-уроки, наповнюватиме базу, описуватиме API і задаватиме формат відповіді для AI.

## 006. Python 3.13 — 2026-11-01

**Рішення:** Python 3.13 (`backend/.python-version`).
**Чому:** вже встановлений, підтримується всіма потрібними бібліотеками. Оновити версію через uv — одна команда.

## 007. Інструменти якості коду — 2026-11-01

**Рішення:** фронтенд — oxlint + Prettier + TypeScript strict; бекенд — ruff (лінтер і форматер) + mypy strict + pytest.
**Чому:** oxlint ставить офіційний шаблон Vite; він значно швидший за ESLint і має правила для React і хуків. ruff замінює flake8, isort і black одним інструментом. mypy strict з першого дня тримає типи всюди, як TypeScript strict на фронті.
**Альтернатива:** ESLint — більша екосистема плагінів; повернемося до нього, якщо бракуватиме правил.

## 008. CI з першого коміту — 2026-11-05

**Рішення:** GitHub Actions на кожен push і PR: ruff, mypy, pytest для бекенду; tsc і oxlint для фронтенду. Автоматичний деплой додамо пізніше в той самий workflow.
**Чому:** перевірки дешеві, поки проєкт маленький, і поломка видна одразу, а не через тиждень. Конфіг ~30 рядків.
**Альтернатива:** запускати перевірки лише локально або налаштувати CI разом із деплоєм — тоді помилки накопичуються непомітно.

## 009. Ранній простий деплой — 2026-11-05

**Рішення:** щойно з'являться акаунти, задеплоїти без Docker: API і база на PaaS (Render / Railway / Fly.io + Neon), фронтенд на Vercel / Netlify. Docker, власний домен і CI/CD-деплой — у v0.4.
**Чому:** живий сайт якомога раніше. Проблеми продакшену — cookie між різними доменами (`SameSite`, `Secure`), CORS з `credentials`, змінні оточення — видно, поки логін щойно написаний, а не через кілька місяців.
**Альтернатива:** перший деплой одразу на Docker + VPS / AWS — довше до живого сайту, і проблеми з логіном з'являються пізно.
